Chapter 13

C와 Zc*: 압축 명령어

RISC-V의 기본 명령은 모두 32비트다. 그런데 프로그램을 들여다보면 addi sp, sp, -16, mv a0, s0, ret처럼 정보가 몇 비트 안 되는 명령이 절반을 넘는다. C 확장은 이런 명령에 16비트짜리 짧은 이름을 붙여 코드 크기를 25–30% 줄인다. 핵심은 “새 명령을 만들지 않는다”는 것이다. 모든 16비트 명령은 이미 있는 32비트 명령 하나로 정확히 펼쳐진다. 이 장에서는 그 약속이 어떤 비트 배치로 실현되는지, 그리고 C를 잘게 나누고 늘린 Zc* 확장이 무엇을 더했는지 직접 압축해 보며 익힌다.

  • 16비트 명령과 32비트 명령이 섞여 있을 때 하드웨어가 길이를 어떻게 알아내는지 설명한다.
  • CR·CI·CSS·CIW·CL·CS·CA·CB·CJ 아홉 형식의 비트 배치와 쓰임새를 구별한다.
  • 3비트 레지스터 칸이 왜 x8–x15를 가리키는지, 즉시값이 왜 4배·16배로 늘어나는지 안다.
  • 주어진 32비트 명령이 압축될 수 있는지 판단하고, 안 된다면 어떤 조건 때문인지 짚는다.
  • Zca·Zcf·Zcd·Zcb·Zcmp·Zcmt의 관계와 Zcmp·Zcmt가 Zcd와 함께 쓰일 수 없는 이유를 안다.
  • IALIGN=16이 명령어 인출 하드웨어에 남기는 숙제(경계에 걸친 명령, 페이지 폴트)를 이해한다.

왜 16비트 명령인가

32비트 고정 길이는 해독기를 단순하게 만든다(4장). 대가는 코드 크기다. ret은 “ra로 점프”라는 정보뿐인데도 32비트를 다 차지한다. 코드가 커지면 마이크로컨트롤러는 플래시 메모리를 더 사야 하고, 큰 서버 프로그램은 명령어 캐시가 넘쳐 느려진다. RISC-V는 이 문제를 압축 명령어(compressed instructions, RVC)로 푼다. 자주 쓰이고 정보가 적은 명령에 한해 16비트 인코딩을 하나 더 정의하는 것이다.

규격 원문에서
“Typically, 50%-60% of the RISC-V instructions in a program can be replaced with RVC instructions, resulting in a 25%-30% code-size reduction.”

Volume I, "C" Extension for Compressed Instructions — 같은 장의 비고는 Waterman의 측정을 인용해, RVC가 인출하는 명령어 비트를 25–30% 줄이고 명령어 캐시 미스를 20–25% 줄인다고, 이는 명령어 캐시를 두 배로 키운 것과 비슷한 효과라고 적는다.

압축 명령어는 RISC-V가 처음 생각한 아이디어가 아니다. 그러나 앞선 RISC들은 처음에 opcode 자리를 남겨 두지 않았기 때문에, 압축 명령을 별도의 ISA로 만들어야 했다. RISC-V는 “25년 뒤늦게 본 덕분에” 처음부터 자리를 비워 두었다.

섞여 있어도 길이를 아는 법: 사분면과 IALIGN

16비트와 32비트 명령이 아무 순서로나 섞여 있으면, 하드웨어는 명령이 어디서 끝나는지 어떻게 알까? 답은 가장 아래 두 비트다. RISC-V의 모든 32비트 명령은 inst[1:0] = 11로 끝난다(4장의 opcode가 모두 …11인 이유). 따라서 아래 두 비트가 00, 01, 10이면 16비트 명령이다. RVC는 이 세 값을 사분면(quadrant) 0·1·2라 부르고, 각 사분면 안에서 inst[15:13](funct3)로 명령을 다시 나눈다.

IALIGN = 16: 명령이 2바이트 경계에서 시작한다

C 확장이 없을 때 명령은 4바이트 경계에만 놓인다(IALIGN=32). C가 있으면 32비트 명령도 2바이트 경계에서 시작할 수 있다(IALIGN=16). 규격은 이렇게 하면 32비트 명령 앞에 2바이트 빈칸(패딩)을 넣지 않아도 되므로 코드 밀도가 크게 좋아진다고 설명한다. 덤으로, C가 있는 시스템에서는 분기·점프 목표 주소가 짝수이기만 하면 되므로 명령 주소 정렬 예외(instruction-address-misaligned)가 아예 일어날 수 없다.

규칙 하나: 16비트 명령은 32비트 명령 하나로 펼쳐진다

RVC의 가장 중요한 설계 제약은 “모든 RVC 명령은 기본 ISA(또는 F·D)의 32비트 명령 정확히 하나로 펼쳐진다”이다. 그래서 하드웨어는 해독 단계 앞에 작은 확장기(expander, decompressor)만 붙이면 되고, 그 뒤의 파이프라인(8장)은 C가 있는지조차 모른다. 컴파일러도 C를 몰라도 된다. 어셈블러와 링커가 알아서 줄여 준다.

모든 비트가 0인 16비트는 영원히 불법 명령

규격은 0x0000을 “정의된 불법 명령”으로 영구히 예약했다. 지워진 메모리나 존재하지 않는 영역(대개 0으로 채워진다)으로 잘못 뛰어들었을 때 곧바로 트랩이 나도록 하기 위해서다. 같은 이유로 모든 비트가 1인 값도 불법 명령으로 남겨 두었다. 비표준 확장도 이 값들을 다른 뜻으로 쓰면 안 된다.

아홉 가지 압축 형식

16비트에 opcode·레지스터·즉시값을 다 넣으려면 무언가를 포기해야 한다. RVC는 세 가지 방법을 섞는다. 첫째, 목적지와 첫 원본을 같게 한다(add rd, rd, rs2처럼 2-주소 형식). 둘째, 레지스터를 3비트로 줄여 가장 많이 쓰는 8개만 가리킨다. 셋째, 즉시값을 짧게 하고 자료 크기만큼 배율을 곱한다. 이 조합에 따라 형식이 아홉 가지로 나뉜다.

3비트 레지스터는 왜 x8–x15인가

CIW·CL·CS·CA·CB 형식의 레지스터 칸(rd′·rs1′·rs2′, 프라임 기호를 붙여 구별한다)은 3비트라 8개밖에 못 가리킨다. 규격은 이 8개를 x8–x15로 정했고, 반대로 ABI 쪽에서 가장 자주 쓰는 레지스터들(s0·s1과 인자 레지스터 a0–a5)이 바로 이 번호에 오도록 호출 규약을 바꿨다(7장). 연속하고 자연스럽게 정렬된 번호 묶음이라 해독기는 3비트 앞에 01만 붙이면 된다. 레지스터가 16개뿐인 RV32E/RV64E와도 그대로 맞는다.

즉시값은 흩어져 있고, 배율이 곱해진다

적재·저장 오프셋은 부호 없는 값이고 자료 크기만큼 배율이 붙는다(워드 ×4, 더블워드 ×8). 정렬된 워드의 주소 하위 두 비트는 어차피 0이니 저장할 필요가 없다. 그 대신 같은 5비트로 4배 먼 곳까지 닿는다. 32비트 명령처럼 즉시값 비트는 흩어져 있는데, 규격은 “되도록 많은 비트가 모든 명령에서 같은 자리에 오도록” 하기 위해서라고 설명한다. 부호 확장이 필요한 즉시값의 부호 비트는 언제나 inst[12]다.

HINT 자리는 왜 남겨 두었나

c.addi a0, 0처럼 아무 효과가 없는 인코딩은 “하는 일 없는 계산”으로 실행해도 되므로, 단순한 구현은 신경 쓸 필요가 없다. 규격은 이런 자리를 성능 힌트용으로 모아 두었다. 실제로 c.add x0, x2–c.add x0, x5 네 자리는 Zihintntl의 c.ntl.*(이번 접근은 다시 안 쓸 데이터라는 힌트)로 쓰인다. RV32C의 HINT 공간 중 78%는 표준용, 나머지는 사용자 정의용이다.

코드 밀도 실험

명령 하나하나보다 중요한 것은 프로그램 전체가 얼마나 줄어드느냐다. 아래 실험은 riscv.js로 프로그램을 어셈블한 뒤 각 명령을 압축기에 넣는다. 분기·점프는 조금 까다롭다. 앞쪽 명령이 줄면 목표까지의 거리도 줄기 때문에, 처음에는 범위를 벗어나던 분기가 압축 가능해질 수 있다. 그래서 실제 링커처럼 배치 → 거리 재계산 → 다시 압축을 더 바뀌지 않을 때까지 되풀이한다(링커 완화, linker relaxation).

16비트 명령은 크기가 절반이므로, 명령의 50–60%가 압축되면 코드 크기는 25–30% 준다. 규격 서두의 숫자가 바로 이 계산이다. 압축률은 컴파일러의 레지스터 배치에 크게 좌우된다. 그래서 컴파일러의 레지스터 할당기는 C가 켜져 있으면 압축하기 좋은 레지스터(x8–x15)를 고르도록 힌트를 주기도 한다(예: LLVM).

Zc*: C를 쪼개고, 늘리고

C 확장은 한 덩어리로 정의되었지만, 쓰다 보니 두 가지 요구가 생겼다. 하나는 나누기다. 부동소수점 압축 적재·저장은 F·D가 있을 때만 의미가 있으니 따로 부를 이름이 필요했다. 다른 하나는 늘리기다. 마이크로컨트롤러 업계는 코드 크기를 더 줄일 명령을 원했다. 그 결과가 Zc* 확장 묶음(v1.0.0)이다.

Zcmp: 프롤로그·에필로그를 한 명령으로

함수 앞뒤에서 ra와 s 레지스터를 스택에 저장하고 되살리는 코드는 정적 코드 크기의 큰 몫을 차지한다. 기본 C를 설계할 때는 load-multiple/store-multiple을 일부러 뺐다. 가상 메모리에서 일부만 실행된 명령을 다시 시작하는 장치가 필요하고, 대응하는 32비트 명령도 없기 때문이다. 대신 공용 저장·복원 루틴을 호출하는 소프트웨어 방법(GCC의 -msave-restore)을 권했다. Zcmp는 임베디드용으로 그 일을 하드웨어 명령으로 되살렸다.

cm.popret은 복원 후 ret까지, cm.popretz는 a0에 0을 넣고 돌아가는 일까지 한 명령으로 한다. 레지스터 목록은 {ra}, {ra, s0}, … {ra, s0-s9}, {ra, s0-s11}의 12가지이고, {ra, s0-s10}은 인코딩 공간을 아끼려고 뺐다. cm.mvsa01(a0·a1 → s 레지스터 두 개)과 cm.mva01s(s 레지스터 두 개 → a0·a1)는 인자를 저장 레지스터로 옮기는 흔한 두 줄을 한 줄로 만든다. 이 명령들은 여러 메모리 접근을 하므로, 도중에 트랩이 나면 처음부터 다시 실행된다. 그래서 sp가 가리키는 메모리는 여러 번 써도 안전한(idempotent) 메모리여야 한다.

Zcmt: 함수 주소를 표로 압축

멀리 있는 함수를 부르려면 auipc + jalr 8바이트가 필요하다. 같은 함수를 여러 곳에서 부른다면, 그 주소를 표에 한 번만 적어 두고 호출은 “표의 몇 번째”로만 하면 된다. 일종의 사전 압축이다. Zcmt의 cm.jt index(index 0–31, 링크 없음)와 cm.jalt index(index 32–255, ra ← pc + 2)가 그 일을 하고, 표의 위치는 새 CSR jvt(주소 0x017, 사용자 모드에서 읽고 쓸 수 있음)가 가리킨다.

MISA.C 비트는 언제 켜지나

misa의 C 비트(17장)는 “C 확장 전체”를 뜻한다. 그래서 Zca만 있고 F가 없거나, RV32에서 Zca·Zcf·F가 있거나, Zca·Zcd·D가 있을 때 켜진다. Zcmp·Zcmt를 쓰는 구현은 Zcd를 가질 수 없으므로, D가 있는 구현에서는 C 비트를 켤 수 없다는 점에 주의하자.

구현의 숙제: 경계에 걸친 명령어

IALIGN=16은 코드 밀도에는 좋지만 명령어 인출 하드웨어에는 숙제를 남긴다. 인출 장치는 보통 4·8·16바이트처럼 정렬된 덩어리(인출 블록, 캐시 라인)를 한 번에 읽는다. 32비트 명령이 2바이트 경계에서 시작하면 앞 절반은 이번 블록에, 뒤 절반은 다음 블록에 있을 수 있다. 그래서 C를 지원하는 코어에는 남은 절반을 잠시 들고 있다가 다음 블록과 이어 붙이는 정렬 버퍼(alignment buffer, instruction queue)가 있다.

페이지 경계에 걸치면: 반쪽짜리 페이지 폴트

더 곤란한 경우는 32비트 명령이 가상 메모리 페이지 경계에 걸칠 때다. 앞 페이지는 메모리에 있고 뒤 페이지는 아직 없으면, 명령의 뒤 절반을 가져오다가 페이지 폴트가 난다. 이때 특권 규격은 mepc(또는 sepc)에는 명령의 시작 주소를 남기고, mtval에 0이 아닌 값을 쓰는 구현이라면 mtval에는 실패한 부분의 주소를 남기도록 정한다. 운영체제는 mtval이 가리키는 페이지를 채운 뒤 mepc로 돌아가 명령 전체를 처음부터 다시 실행한다(18장, 19장).

고성능 코어에서의 비용과 이득

여러 명령을 한 사이클에 해독하는 슈퍼스칼라 코어는 각 명령의 시작 위치를 먼저 찾아야 한다. RVC는 2바이트 묶음마다 하위 두 비트만 보면 길이를 알 수 있어 이 일이 x86처럼 어렵지는 않지만, 명령 경계를 찾는 회로와 정렬 버퍼는 분명히 추가 비용이다. 이 비용 때문에 응용 프로세서 쪽 일부에서는 C를 의무로 둘지 논쟁이 있었다. 반대로 인출 대역폭과 명령어 캐시 용량을 25–30% 아끼는 효과는 고성능 코어에도 그대로 이득이다. 현재 RVA 프로파일(23장)은 C를 포함한다.

핵심 정리

  1. C 확장은 자주 쓰는 명령에 16비트 인코딩을 더해 코드 크기를 보통 25–30% 줄인다. 명령어 캐시 효율과 인출 대역폭도 함께 좋아진다.
  2. inst[1:0] ≠ 11이면 16비트 명령이다. 세 값이 사분면 0·1·2이고, 각 사분면은 funct3로 다시 나뉜다. C가 있으면 IALIGN=16이 되어 32비트 명령도 2바이트 경계에서 시작할 수 있다.
  3. 모든 RVC 명령은 기본 ISA(또는 F·D)의 32비트 명령 하나로 펼쳐진다. 하드웨어는 해독 앞단의 확장기만, 컴파일러는 아무것도 바꾸지 않아도 된다.
  4. 아홉 형식(CR·CI·CSS·CIW·CL·CS·CA·CB·CJ)은 2-주소 형식, 3비트 레지스터(x8–x15), 짧고 배율이 붙은 즉시값을 조합한 결과다.
  5. Zca·Zcf·Zcd는 C를 쪼갠 이름이고, Zcb는 단순한 16비트 명령을, Zcmp는 push/pop을, Zcmt는 표 점프와 jvt CSR(0x017)을 더한다. Zcmp·Zcmt는 c.fsdsp 자리를 다시 쓰므로 Zcd와 함께 쓸 수 없다.
  6. 2바이트 정렬 때문에 32비트 명령이 인출 블록이나 페이지 경계에 걸칠 수 있다. 정렬 버퍼가 이를 이어 붙이고, 페이지 폴트가 나면 mepc는 명령의 시작, mtval은 실패한 부분을 가리킨다.

확인 퀴즈

메모리에서 읽은 16비트 묶음의 하위 두 비트가 10이다. 이 명령은?

32비트 명령은 하위 두 비트가 반드시 11이다. 00·01·10은 각각 RVC 사분면 0·1·2다.

CL 형식 c.lw의 rd′ 칸이 010이다. 실제 목적지 레지스터는?

3비트 레지스터 칸은 x8–x15를 가리킨다. 앞에 01을 붙이면 01010 = x10 = a0이다.

다음 중 압축할 수 없는 명령은?

c.lw의 오프셋은 5비트 × 4 = 0–124다. 128은 범위를 넘는다. 나머지는 각각 c.lw, c.swsp(0–252), c.addi16sp(−512–496, 16의 배수)로 줄어든다.

“모든 RVC 명령은 32비트 명령 하나로 펼쳐진다”는 제약이 주는 이득으로 맞지 않는 것은?

규격은 여러 명령을 하나로 합치는 더 촘촘한 인코딩의 이득보다 1:1 대응이 주는 단순함이 훨씬 크다고 판단했다. load/store-multiple을 기본 C에서 뺀 이유이기도 하다.

RV64C에서 RV32C의 c.jal 인코딩 자리는 무엇으로 쓰이나?

사분면 1의 funct3 = 001은 RV32에서는 c.jal, RV64에서는 c.addiw다. 짧은 호출은 작은 RV32 프로그램에서 더 흔하고, RV64에서는 32비트 덧셈 후 부호 확장이 자주 필요하기 때문이다.

RV64GC(= C와 D를 모두 가진) 프로세서에 Zcmp를 더할 수 없는 이유는?

C+D이면 Zcd가 포함되고, Zcd의 c.fsdsp 자리를 Zcmp(와 Zcmt)가 재사용하므로 둘은 공존할 수 없다.

16비트 값 0x0000을 실행하면?

모든 비트가 0인 16비트 명령은 0으로 채워진 메모리로 잘못 뛰어든 경우를 잡기 위해 영구히 불법 명령으로 정의되어 있다. 참고로 c.nop은 0x0001이다.

0x2ffe에서 시작하는 32비트 명령의 뒤 절반(0x3000)을 인출하다 페이지 폴트가 났다. mepc와 mtval은?

mepc는 다시 실행할 명령의 시작을, mtval(0이 아닌 값을 쓰는 구현이라면)은 폴트를 일으킨 부분의 주소를 가리킨다. C가 있는 시스템에서는 명령 주소 정렬 예외가 일어날 수 없다.
