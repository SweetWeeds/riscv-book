Chapter 11

RVWMO 메모리 모델

하트 0이 x = 1을 쓰고 이어서 y = 1을 썼다. 하트 1이 y에서 1을 읽었다면 x도 당연히 1일까? RISC-V에서는 아니다. 서로 다른 주소에 대한 메모리 접근은 다른 하트가 보기에 순서가 바뀔 수 있다. 어떤 순서 바뀜이 허용되고 어떤 것은 금지되는지를 정한 규칙이 메모리 일관성 모델이고, RISC-V의 모델 이름이 RVWMO(RISC-V Weak Memory Ordering)다. 이 장에서는 저장 버퍼에서 시작해 RVWMO의 정의, FENCE, 리트머스 테스트, 그리고 C/C++ 원자 연산이 어떻게 번역되는지까지 따라간다.

  • 저장 버퍼·캐시·비순차 실행 때문에 다른 하트가 순서 바뀐 결과를 볼 수 있음을 설명한다.
  • 순차 일관성(SC), TSO, RVWMO가 허용하는 재배치를 비교한다.
  • 프로그램 순서, 전역 메모리 순서, 보존 프로그램 순서(PPO)를 구별한다.
  • PPO 13개 규칙을 네 무리(주소 겹침·명시적 동기화·구문 의존성·파이프라인 의존성)로 정리한다.
  • Load Value·Atomicity·Progress 세 공리를 안다.
  • FENCE의 fm·pred·succ 필드를 인코딩하고 fence.tso의 뜻을 안다.
  • MP·SB·LB·2+2W 리트머스 테스트의 결과를 모델별로 예측하고 C/C++ 매핑을 읽는다.

왜 메모리 모델이 필요한가

하트 하나만 보면 모든 것이 프로그램 순서대로 일어나는 것처럼 보인다. 그런데 하드웨어 내부는 그렇지 않다. 성능을 위해 거의 모든 코어가 다음과 같은 장치를 쓴다.

  • 저장 버퍼(store buffer) — store는 캐시에 바로 쓰지 않고 버퍼에 넣어 둔 뒤 나중에 내보낸다. 그동안 뒤의 load는 기다리지 않고 먼저 메모리로 간다.
  • 비순차 실행 — 주소가 먼저 계산된 load부터 실행한다. 캐시 미스가 난 load 뒤의 load가 먼저 값을 받아 올 수 있다.
  • 캐시와 연결망 — 여러 코어의 쓰기가 서로 다른 경로로 퍼져 나가 도착 순서가 달라질 수 있다.

내 하트 안에서는 이런 재배치가 감춰진다(내가 쓴 값은 내가 곧바로 다시 읽을 수 있다). 하지만 다른 하트는 그 효과를 다른 순서로 볼 수 있다.

이 효과가 실제로 어떤 결과를 낳는지 아래 애니메이션에서 단계별로 확인해 보자. 두 하트가 각자 자기 변수에 1을 쓰고 상대 변수를 읽는다. 사람이 생각하는 “한 번에 하나씩” 실행이라면 둘 다 0을 읽는 일은 불가능하다. 적어도 한쪽의 쓰기가 먼저 끝났을 테니까.

SC, TSO, 그리고 RVWMO

메모리 모델은 “다른 하트가 볼 수 있는 결과의 집합”을 정한다. 강한 모델일수록 프로그래머가 생각하기 쉽고, 약한 모델일수록 하드웨어가 빨라질 여지가 크다.

RVWMO의 뼈대: 프로그램 순서, 전역 메모리 순서, PPO

RVWMO는 세 가지 순서로 정의된다.

  • 프로그램 순서(program order) — 한 하트의 동적 명령 흐름에서 메모리 연산이 놓인 순서. 단순한 순차 프로세서가 실행할 순서다.
  • 전역 메모리 순서(global memory order) — 모든 하트의 메모리 연산을 한 줄로 세운 전체 순서. 실행마다 하나씩 있다.
  • 보존 프로그램 순서(preserved program order, PPO) — 프로그램 순서 가운데 전역 메모리 순서가 반드시 지켜야 하는 부분 집합.

RVWMO의 정의는 한 문장으로 요약된다. “PPO를 지키고 세 공리(Load Value, Atomicity, Progress)를 만족하는 전역 메모리 순서가 하나라도 존재하는 실행은 합법이다.” 그러니 PPO에 무엇이 들어 있는지가 곧 “무엇이 재배치되지 않는가”의 목록이다.

세 공리: Load Value, Atomicity, Progress

PPO를 지키는 전역 메모리 순서가 있다고 해서 아무 값이나 읽을 수 있는 것은 아니다. load가 무엇을 돌려주는지, LR/SC가 언제 원자적인지, 연산이 영원히 미뤄질 수 있는지를 세 공리가 정한다.

공리내용 (요약)
Load Valueload의 각 바이트는, 그 바이트를 쓰는 store 가운데 ① 전역 메모리 순서상 load보다 앞선 것과 ② 프로그램 순서상 load보다 앞선 것을 모두 모아, 그중 전역 메모리 순서가 가장 늦은 store의 값을 돌려준다.
Atomicity짝을 이룬 LR(r)과 SC(w)에서, r이 store s의 값을 읽었다면 s는 w보다 앞서고, s와 w 사이에 다른 하트가 그 바이트에 쓴 store가 끼어들 수 없다.
Progress어떤 메모리 연산도 무한히 많은 다른 연산 뒤로 밀릴 수 없다. (쓴 값은 결국 다른 하트에게 보인다)
RVWMO는 multi-copy atomic이다

전역 메모리 순서가 하나라는 것은, 어떤 store가 한 다른 하트에게 보였다면 모든 다른 하트에게도 같은 순서로 보인다는 뜻이다(자기 하트의 저장 버퍼 전달만 예외). Power나 옛 Arm처럼 하트마다 다른 순서로 store를 볼 수 있는 non-multi-copy-atomic 모델보다 추론하기 쉽다. 규격 부록에는 이 모델을 Alloy·Herd 형식으로 쓴 공리적 정의와, 동등한 동작(operational) 모델이 함께 실려 있다.

FENCE: 순서를 명시하는 명령

PPO 규칙 4가 말하는 FENCE는 기본 정수 ISA(5장)의 일부다. FENCE 앞의 선행 집합(predecessor set)에 속한 연산을, 뒤의 후행 집합(successor set)에 속한 연산보다 먼저 일어난 것으로 모든 하트와 외부 장치가 보게 만든다. 집합은 네 종류를 조합한다: 장치 입력(I), 장치 출력(O), 메모리 읽기(R), 메모리 쓰기(W).

리트머스 테스트로 모델 시험하기

메모리 모델은 리트머스 테스트(litmus test)라는 아주 짧은 다중 하트 프로그램으로 이야기한다. 각 테스트에는 “이 결과가 나올 수 있는가?”라는 질문이 하나 붙는다. 규격 부록(Explanatory Material)도 수십 개의 리트머스 테스트로 RVWMO의 미묘한 부분을 설명한다. 가장 유명한 네 가지를 보자. 모든 변수는 0에서 시작한다.

언어 원자 연산의 번역과 Ztso

프로그래머는 보통 FENCE를 직접 쓰지 않는다. C/C++의 std::atomic이나 Linux 커널의 동기화 함수가 메모리 모델을 감싸 준다. 규격 부록은 이 연산들을 RISC-V 명령으로 바꾸는 권장 매핑을 표로 싣고 있다. 아래는 그중 C/C++ 표(Table 16)의 핵심이다.

Ztso: TSO를 약속하는 확장

x86이나 SPARC용 코드는 TSO를 가정하고 FENCE 없이 쓰인 경우가 많다. Ztso(v1.0)는 새 명령 없이 “이 구현은 RVTSO를 따른다”는 약속만 추가한다. 규격의 정의는 RVWMO에서의 차이로 주어진다.

  • 모든 load는 acquire-RCpc 표시가 있는 것처럼 동작한다.
  • 모든 store는 release-RCpc 표시가 있는 것처럼 동작한다.
  • 모든 AMO는 acquire-RCsc와 release-RCsc 표시가 모두 있는 것처럼 동작한다.

이 때문에 PPO 규칙 4–7을 뺀 나머지는 모두 중복이 되고, PW와 SR을 모두 갖지 않은(메모리) FENCE도 중복이 된다. 남는 재배치는 store → 뒤의 load 하나뿐이다. V 확장의 벡터 메모리 명령도 명령 단위로는 RVTSO를 따르지만, 한 명령 안의 원소 접근 순서까지 강해지지는 않는다.

규격 원문에서
“In spite of the fact that Ztso adds no new instructions to the ISA, code written assuming RVTSO will not run correctly on implementations not supporting Ztso.”

"Ztso" Extension for Total Store Ordering, Version 1.0 — 그래서 Ztso 전용으로 컴파일한 바이너리는 그 사실을 표시해, Ztso가 없는 플랫폼이 실행을 거부할 수 있게 해야 한다.

핵심 정리

  1. 저장 버퍼·비순차 실행·캐시 때문에 다른 하트는 내 메모리 접근을 다른 순서로 볼 수 있다. 메모리 모델은 허용되는 결과의 집합을 정한다.
  2. RISC-V 기본 모델 RVWMO(v2.0)는 서로 다른 주소에 대한 네 종류(W→R, W→W, R→R, R→W) 재배치를 모두 허용하는 약한 모델이지만, 전역 메모리 순서가 하나인 multi-copy atomic 모델이다.
  3. 실행은 PPO를 지키고 Load Value·Atomicity·Progress 공리를 만족하는 전역 메모리 순서가 있으면 합법이다.
  4. PPO 13규칙은 주소 겹침(1–3), 명시적 동기화(4–8: FENCE, acquire, release, RCsc, LR/SC 짝), 구문 의존성(9–11: 주소, 데이터, store로의 제어), 파이프라인 의존성(12–13)으로 나뉜다.
  5. FENCE는 fm[31:28], pred[27:24] = PI PO PR PW, succ[23:20] = SI SO SR SW로 인코딩한다. fence.tso(fm = 1000, RW,RW)는 쓰기→읽기만 빼고 순서를 정한다.
  6. MP·LB·2+2W의 문제 결과는 RVWMO에서만, SB의 0/0은 TSO와 RVWMO 모두에서 허용된다. MP는 fence w,w + fence r,r, SB는 양쪽 fence rw,rw로 막는다.
  7. C/C++ acquire load는 l; fence r,rw, release store는 fence rw,w; s로 번역한다. Ztso는 모든 load·store에 RCpc acquire/release를 부여해 TSO를 약속한다.

확인 퀴즈

TSO에서도 허용되는 재배치는?

TSO의 유일한 완화는 저장 버퍼 때문에 생기는 store→load 재배치다. RVWMO는 네 가지 모두 허용한다.

MP 테스트에서 r1 = 1, r2 = 0을 RVWMO에서 막는 가장 가벼운 조합은?

쓰는 쪽은 데이터→플래그 쓰기 순서를, 읽는 쪽은 플래그→데이터 읽기 순서를 지켜야 한다. 제어 의존성은 load를 묶지 못한다. fence.tso는 W→W와 R→R을 모두 묶으므로 양쪽에 넣으면 막힌다.

PPO 규칙 11(제어 의존성)이 순서를 보장하는 경우는?

분기에 의존하는 store만 순서가 보장된다. 투기적 실행으로 분기 뒤의 load를 미리 실행하는 것은 허용된다.

fence.tso의 인코딩으로 옳은 것은?

fm = 1000, pred = RW(0011), succ = RW(0011)이다. 0x0330000f는 fence rw,rw, 0x0100000f는 pause, 0x0ff0000f는 fence iorw,iorw다.

하트가 자기 저장 버퍼의 값을 먼저 읽어 오는 것(전달)을 허용하는 RVWMO의 조항은?

Load Value 공리는 전역 순서상 앞선 store뿐 아니라 프로그램 순서상 앞선 같은 하트의 store도 후보로 삼는다. 그래서 load가 전역 순서에서 자기 store보다 앞에 있어도 그 값을 읽을 수 있다.

C/C++ atomic_store(memory_order_release)의 RVWMO 권장 매핑은?

release는 “앞의 모든 접근이 이 store보다 먼저 보이게” 해야 하므로 FENCE를 store 앞에 두고 pred = RW, succ = W를 쓴다.

Ztso에 대한 설명으로 옳은 것은?

Ztso는 명령을 추가하지 않는다. 그 대신 TSO를 가정한 코드는 Ztso가 없는 구현에서 틀리게 동작할 수 있으므로 바이너리에 표시해야 한다. 쓰기→읽기 순서가 필요하면 여전히 FENCE가 필요하다.
